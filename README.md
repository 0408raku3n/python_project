# Проект "PySemModel" - Python Semantic Model Builder

## Проблема
Заключается в отсутствии единой удобной среды, которая объединяет возможности LLM с формализованным хранением знаний и позволяет автоматически строить, анализировать, проверять и изменять семантическую модель предметной области.

## Цель
Разработать Python-приложение, которое использует большую языковую модель (LLM) для построения, хранения, анализа и изменения семантической модели знаний.

## Ожидаемые пользователи
Основными пользователями приложения являются специалисты, которым необходимо формировать и поддерживать структурированное представление знаний о некоторой предметной области.
- Исследователи и аналитики. Для систематизации информации, выявления взаимосвязей между понятиями и анализа сложных предметных областей.
- Разработчики программного обеспечения и системные архитекторы. Для моделирования предметных областей, описания сущностей и связей между компонентами системы, а также управления знаниями о программных системах.
- Эксперты предметных областей. Для создания и уточнения семантических моделей, проверки корректности связей и внесения изменений без необходимости вручную работать с формальными структурами данных.
- Специалисты по управлению знаниями. Для объединения информации из различных источников, устранения дублирования и поддержания актуальности базы знаний.
- Разработчики интеллектуальных приложений. Для использования семантической модели как структурированной базы знаний в системах на основе LLM, включая интеллектуальный поиск и системы поддержки принятия решений.

На начальном этапе целевой аудиторией могут стать разработчики и исследователи, которым нужен инструмент для экспериментов с построением и анализом графов знаний с использованием LLM.

## Функциональные возможности
Предлагается реализовать следующие функциональные возможности:

1. **Построение семантической модели знаний**
Приложение принимает текстовые данные или описание предметной области на естественном языке. LLM извлекает из них сущности, понятия, свойства и отношения, после чего приложение формирует структурированную модель знаний, например в виде семантического графа.
2. **Хранение и управление знаниями**
Система обеспечивает сохранение модели в постоянном хранилище, загрузку и экспорт данных, добавление и удаление сущностей и связей, а также обновление свойств существующих элементов.
3. **Семантический поиск и анализ**
Пользователь задаёт вопросы на естественном языке, а приложение преобразует их в запросы к модели знаний. Система позволяет находить связанные понятия, исследовать цепочки отношений, выявлять зависимости и получать ответы с опорой на сохранённые данные.
4. **Изменение модели с помощью LLM**
Пользователь описывает требуемые изменения на естественном языке. LLM формирует набор предполагаемых операций над моделью, а приложение проверяет их корректность и применяет после подтверждения пользователя, если оно требуется.
5. **Проверка целостности и согласованности**
Система обнаруживает дублирующиеся сущности, некорректные связи, противоречивые сведения и нарушения заданных правил модели. Результаты анализа используются для подготовки рекомендаций по исправлению ошибок.
6. **Отслеживание изменений и происхождения знаний**
Система сохраняет историю изменений модели и, по возможности, ссылки на источники, из которых были извлечены факты. Пользователь может просматривать предыдущие версии и выяснять, на каких данных основано конкретное утверждение.
7. **Визуализация семантической модели**
Приложение предоставляет графическое представление модели в виде узлов и рёбер. Пользователь может изучать структуру знаний, переходить между связанными элементами и просматривать свойства сущностей.

## Основные пользовательские сценарии

### Создание семантической модели
**Цель:** построить первоначальную семантическую модель знаний на основе текстового описания предметной области.

**Входные данные:**
- Текстовое описание предметной области.
- Название и, при необходимости, описание модели.
- Инструкции по структуре модели или правила выделения сущностей и отношений (опционально).
  
**Ожидаемое поведение:**
- Приложение принимает описание предметной области.
- LLM анализирует текст, выделяет сущности, понятия, свойства и отношения между ними.
- Приложение преобразует результат анализа в формализованную структуру, например граф знаний.
- Система проверяет структурную корректность модели, выявляет дублирующиеся сущности и некорректные связи.
- Пользователь получает возможность просмотреть результат и подтвердить создание модели.
- Приложение сохраняет модель в постоянном хранилище.
  
**Результат:** Созданная и сохранённая семантическая модель, содержащая идентифицированные сущности, их свойства и отношения. Пользователь может просматривать и анализировать её, а также выполнять последующие операции.

### Ответ на вопрос по модели знаний
**Цель:** получить ответ на вопрос на естественном языке на основе информации, содержащейся в семантической модели.

**Входные данные:**
- Идентификатор или выбор семантической модели.
- Вопрос пользователя на естественном языке.
  
**Ожидаемое поведение:**
- Приложение принимает вопрос пользователя.
- LLM интерпретирует вопрос и определяет, какие сведения необходимо получить.
- Система выполняет поиск по модели знаний, извлекая релевантные сущности, свойства и отношения.
- При необходимости приложение исследует цепочки связей между сущностями.
- LLM формирует ответ на основе найденных данных.
- Система указывает источники или элементы модели, на которых основан ответ, и сообщает, если имеющихся знаний недостаточно.
  
**Результат:** Ответ на естественном языке, основанный на содержимом модели знаний, с возможностью проследить, какие факты и связи использовались для его формирования.

### Точечное обновление семантической модели
**Цель:** изменить отдельные элементы существующей модели без её полного перестроения.

**Входные данные:**
- Идентификатор семантической модели.
- Текстовая инструкция пользователя, описывающая требуемое изменение.
Пример: «Измени должность Анны Ивановой на руководителя отдела аналитики и укажи, что она подчиняется генеральному директору».

**Ожидаемое поведение:**
- Приложение принимает инструкцию и определяет целевые сущности и отношения.
- LLM преобразует инструкцию в набор структурированных операций: создание, изменение или удаление сущностей, свойств и связей.
- Система проверяет существование целевых объектов, корректность операций и соблюдение ограничений модели.
- Приложение формирует предварительное представление изменений для проверки пользователем, если это предусмотрено режимом работы.
- После подтверждения система применяет изменения к модели.
- Приложение сохраняет обновлённую версию и регистрирует выполненные операции.
  
**Результат:** Обновлённая семантическая модель, в которой изменены только целевые элементы и необходимые связи. Остальная часть модели сохраняется без изменений. История позволяет определить, что именно было изменено.

### Загрузка нового документа
**Цель:** дополнить существующую семантическую модель знаниями из нового документа.

**Входные данные:**
- Идентификатор семантической модели, которую необходимо дополнить.
- Документ в поддерживаемом формате, например PDF, DOCX или TXT.
- Дополнительные инструкции по обработке документа (опционально).
  
**Ожидаемое поведение:**
- Приложение принимает документ и извлекает из него текст.
- LLM анализирует содержимое и выделяет новые факты, сущности, свойства и отношения.
- Система сопоставляет извлечённые данные с существующей моделью.
- Приложение определяет, какие сущности и связи уже существуют, какие необходимо добавить, а какие сведения могут противоречить имеющимся.
- Система формирует набор предполагаемых изменений и проверяет его структурную корректность.
- Пользователь может просмотреть новые знания, обнаруженные совпадения и противоречия.
- После подтверждения приложение вносит изменения и сохраняет ссылку на исходный документ как источник добавленных сведений.
  
**Результат:** Расширенная семантическая модель, дополненная знаниями из документа. Повторяющиеся сущности по возможности объединены с существующими, потенциальные противоречия выделены для проверки, а происхождение новых сведений зафиксировано.

## Minimum Viable Product (MVP)
В рамках MVP реализуется минимальная версия приложения для построения, хранения и изменения семантической модели знаний с использованием LLM.

### Границы
В состав MVP входит:
- Один локальный граф. Приложение работает с одной семантической моделью, хранящейся локально. Поддержка нескольких независимых графов и совместной работы пользователей не входит в MVP.
- Текстовые входные данные. Все пользовательские запросы и исходные данные передаются в текстовом виде. Загрузка документов в рамках MVP ограничивается извлечением знаний из предоставленного текста; обработка PDF, DOCX и других форматов файлов не предусматривается.
- Отсутствие графического интерфейса. Взаимодействие с приложением осуществляется через командную строку или программный API. Визуализация графа и веб-интерфейс не реализуются.
- Отсутствие внешней базы данных. Граф хранится в локальном файле или другом локальном формате сериализации. Подключение серверных СУБД и внешних хранилищ не предусмотрено.

В пределах этих границ MVP должен поддерживать четыре основных сценария: **создание модели из текста, ответы на вопросы по модели, точечное обновление знаний и дополнение модели содержимым нового текстового документа.**

### Ограничения
В рамках MVP имеются следующие свойства и недостатки выбранной реализации:
1. Ошибки извлечения знаний. LLM может неверно определять сущности, свойства и отношения, пропускать важные факты или интерпретировать текст неоднозначно. Автоматически построенная модель может содержать неточности.
2. Ограниченная проверка корректности. Проверки будут выявлять основные структурные ошибки, дубликаты и некоторые противоречия. Полная проверка логической согласованности знаний не гарантируется.
3. Ограниченность поиска по графу. Поиск будет опираться на явно сохранённые сущности и отношения. Система может не находить неочевидные связи, выполнять только ограниченное исследование цепочек отношений и не поддерживать сложные логические выводы.
4. Зависимость от качества исходных данных. Неполные, противоречивые или плохо структурированные тексты могут приводить к неполной или некорректной модели знаний.
5. Ограниченная обработка документов. Первая версия ориентирована на текстовые входные данные. Извлечение текста из сложных документов, обработка таблиц, изображений и сканированных страниц не предусматриваются.
6. Ограничения точечного обновления. LLM может неверно определить, какие элементы модели необходимо изменить. Поэтому изменения должны проходить проверку, а потенциально неоднозначные операции — требовать подтверждения пользователя.
7. Отсутствие полноценного управления версиями. История операций может фиксироваться в упрощённом виде, без развитых механизмов сравнения версий, автоматического разрешения конфликтов и восстановления произвольного состояния модели.
8. Ограничения производительности и масштабирования. Локальное хранение и обработка графа рассчитаны на небольшие и средние объёмы знаний. При росте количества сущностей и связей поиск и обновление могут замедляться.
9. Зависимость от используемой LLM. Качество результатов, время обработки и стоимость запросов зависят от выбранной модели и способа её подключения. Ответы LLM не следует считать гарантированно достоверными.
10. Отсутствие многопользовательского режима. Первая версия не предусматривает одновременное редактирование графа несколькими пользователями, разграничение прав доступа и синхронизацию между устройствами.

## Правила именований
Для обеспечения единообразия кода и упрощения дальнейшего развития проекта вводятся общие правила именования файлов, директорий, программных компонентов и основных понятий предметной области.

### Имя проекта
Имя проекта должно быть коротким, понятным и отражать назначение приложения. Для имени репозитория и Python-пакета используется snake_case — строчные латинские буквы, слова разделяются символом _.
Рекомендуемое рабочее имя: '''semantic_knowledge'''

### Именование директорий и файлов
- Директории и файлы Python именуются в snake_case, например knowledge_graph.py, document_loader.py.
- Названия директорий должны отражать назначение содержащихся в них компонентов, например models/, storage/, llm/, services/, tests/.
- Тестовые файлы именуются с префиксом test_, например test_knowledge_graph.py.
- Конфигурационные файлы используют общепринятые имена и форматы, например pyproject.toml, .env.example.
- Названия файлов должны быть информативными и не содержать избыточных сокращений.

### Именование элементов Python-кода
Именование должно проводиться в соответствии с рекомендациями PEP 8:
- Модули и переменные: snake_case, например knowledge_graph, entity_id.
- Функции и методы: snake_case, например extract_entities(), update_relation().
- Классы: PascalCase, например KnowledgeGraph, DocumentProcessor.
- Константы: UPPER_SNAKE_CASE, например DEFAULT_MODEL, MAX_SEARCH_DEPTH.
- Приватные атрибуты и методы: префикс _, например _validate_graph().

Названия должны отражать смысл операции или объекта, а не детали реализации.

### Основные понятия предметной области
В проекте необходимо использовать единый словарь терминов, чтобы одинаковые сущности и операции не назывались по-разному в разных модулях.
- **Knowledge Graph** - семантический граф, представляющий знания в виде сущностей и отношений
- **Entity** - сущность предметной области, представленная узлом графа
- **Relation** - отношение между сущностями, представленное ребром графа
- **Property** - свойство сущности или отношения
- **Knowledge Model** - структурированное представление знаний, используемое приложением
- **LLM** - большая языковая модель, используемая для извлечения и интерпретации знаний
- **Document** - текстовый документ — источник информации для построения или обновления модели
- **Query** - запрос пользователя к модели знаний
- **Extraction** - извлечение сущностей, свойств и отношений из текста
- **Update** - изменение существующей модели знаний
- **Validation** - проверка структурной корректности и соблюдения ограничений модели

### Общие правила терминологии
- В коде используются английские названия, в документации допускаются русские описания с английскими терминами при первом упоминании.
- Один термин должен обозначать одно понятие во всём проекте.
- Названия сущностей предметной области следует отделять от технических компонентов. Например, Entity обозначает элемент графа, а EntityExtractor — компонент, который извлекает сущности из текста.
- Для идентификаторов сущностей и отношений следует использовать стабильные ID, не зависящие от их отображаемых названий.
- Названия функций должны обозначать конкретное действие: create_graph(), find_entities(), apply_update().
- Сокращения допускаются для общепринятых терминов, таких как LLM и API.
