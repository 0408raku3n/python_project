# Файловое хранение семантического графа в DOT

## Статус и границы

Документ предлагает формат одного локального графа. Семантическая модель ещё не согласована: имена и состав атрибутов, типы сущностей и отношений, версия схемы, правила идентификаторов и ревизий требуют сверки с `docs/semantic-model.md` после её появления. До согласования примеры и контракт ниже предварительные.

Файл UTF-8 содержит граф и его метаданные. Чтение не должно изменять файл; сохранение допустимо только после проверки всего графа. Формат предназначен для ручного просмотра и редактирования. Определение алгоритма атомарной записи и истории ревизий относится к реализации хранилища.

## Поддерживаемое подмножество

В файле ровно один именованный `digraph` с именем `semantic_graph`. Внутри допустимы один оператор `graph [...]` для атрибутов графа, явные объявления узлов и отдельные направленные связи `source -> target [...]`. Каждое объявление узла и связи содержит один список атрибутов; имена атрибутов в одном списке не повторяются. Порядок объявлений при чтении произвольный. Пробелы и комментарии DOT допускаются, но при сохранении комментарии не сохраняются.

Каждый конец связи должен иметь отдельное явное объявление узла в том же графе. Само упоминание идентификатора в связи не считается объявлением, хотя стандартный DOT допускает неявное создание узла. Параллельные связи и петли допустимы, если идентификаторы связей различаются. Объявление одного узла несколько раз — ошибка, даже если стандартный DOT допускает объединение атрибутов.

Не поддерживаются `strict`, неориентированный `graph` и оператор `--`, подграфы и кластеры, порты и точки привязки, цепочки связей (`a -> b -> c`), множества узлов в связях, объявления значений по умолчанию `node [...]` и `edge [...]`, отдельные присваивания атрибутов графа, HTML-подобные значения и конкатенация строк оператором `+`. Не допускаются несколько графов или произвольные операторы за его пределами. Неподдерживаемые конструкции не преобразуются молча.

## Атрибуты и идентификаторы

Все значения в DOT записываются строками в двойных кавычках; типы ниже проверяются после чтения. Прочие атрибуты в этой версии не допускаются, в том числе атрибуты оформления Graphviz. Пустые обязательные значения и повторение имени атрибута — ошибки. Сравнение имён и идентификаторов чувствительно к регистру.

| Объект | Обязательное поле | Тип и ограничение |
|---|---|---|
| Граф | `schema_version` | Строка `"1"`; неизвестная версия отклоняется. |
| Граф | `revision` | Неотрицательное целое в десятичной записи: `0` или число без ведущих нулей. |
| Узел | идентификатор в DOT | Строка по правилу ниже, уникальная среди узлов. |
| Узел | `label` | Непустая строка Unicode — отображаемое название. |
| Связь | `id` | Строка по правилу ниже, уникальная среди всех связей графа. |
| Связь | `label` | Непустая строка Unicode — отображаемое название отношения. |

Идентификатор узла и `id` связи соответствуют `[A-Za-z][A-Za-z0-9_-]*` и сохраняются в двойных кавычках. Пространства идентификаторов узлов и связей раздельны. Идентификатор назначается при создании и не меняется при переименовании или изменении свойств; он не выводится из `label`. Одинаковые названия сами по себе не означают одинаковую сущность. Две связи с одинаковыми концами и названиями остаются различными при разных `id`.

`schema_version` определяет контракт файла, а `revision` — состояние графа: новый граф начинает с `0`, каждое успешно сохранённое семантическое изменение увеличивает ревизию на единицу; сохранение без изменения графа её не увеличивает. Ручное редактирование должно сопровождаться соответствующим увеличением ревизии. Механизм обнаружения конкурентных изменений и хранения предыдущих состояний требует отдельного решения.

## Строки и сохранение

Файл кодируется в UTF-8 без BOM; кириллица и другие символы Unicode записываются непосредственно. Для строковых значений допускаются `\"` для кавычки, `\\` для обратной косой черты и `\n` для перевода строки. Другие последовательности после обратной косой черты, включая специальные подстановки Graphviz, и буквальные управляющие символы внутри значения отклоняются. Переносы строк в данных нормализуются к LF и записываются как `\n`; буквальная последовательность из обратной косой черты и буквы `n` записывается как `\\n`. Нормализация самих символов Unicode не выполняется. Это правила данных приложения; результат визуализации может зависеть от Graphviz.

При сохранении используются двойные кавычки для идентификаторов и значений, по одному оператору на строку, LF и завершающий перевод строки. Сначала записывается оператор атрибутов графа, затем узлы по идентификатору, затем связи по кортежу `(source, target, id)`; внутри каждого списка атрибуты сортируются по имени. Сравнение строк для сортировки — по кодовым точкам Unicode, без учёта локали. Одинаковый граф и ревизия дают одинаковый текст независимо от порядка входных объявлений.

## Проверка и диагностика

Синтаксическая корректность DOT необходима, но недостаточна: стандартный обработчик DOT может принять файл, нарушающий правила выше. Проверка выполняется без потери исходных объявлений и атрибутов, чтобы обнаружить неявные узлы и дубликаты до возможного объединения стандартным обработчиком. Отклонение файла не должно приводить к частичному сохранению или исправлению данных.

| Ситуация | Код диагностики | Что сообщить |
|---|---|---|
| Некорректный UTF-8 или повреждённый синтаксис DOT | `INVALID_DOT` | Причину и позицию, если она известна. |
| Конструкция за пределами подмножества | `UNSUPPORTED_DOT` | Конструкцию и её положение. |
| Отсутствующее, неизвестное или повторённое поле; неверный тип или значение | `INVALID_ATTRIBUTE` | Объект, имя поля и причину; неизвестную версию схемы указать явно. |
| Повторное объявление узла или повторный `id` связи | `DUPLICATE_ID` | Вид и идентификатор объекта. |
| Связь с необъявленным узлом | `MISSING_NODE` | Идентификатор связи и отсутствующий конец. |

Диагностика включает путь к файлу, код, понятное сообщение и строку с колонкой, когда их можно определить. Если позиция неизвестна, она явно отсутствует; нельзя сообщать вымышленную позицию. При нескольких ошибках допускается сообщить все надёжно определённые ошибки; после синтаксической ошибки дальнейшая проверка может быть невозможна.
