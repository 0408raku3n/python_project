# ADR-0001. DOT как формат хранения семантической модели

- **Статус:** Принято
- **Дата:** 2026-11-04

## Контекст

Семантическая модель должна сохраняться между запусками, быть читаемой и редактируемой человеком, допускать сравнение версий в Git и не требовать внешней базы данных на этапе MVP. Модель содержит узлы, направленные связи и атрибуты; возможны циклы и параллельные связи.

## Решение

Основным сохраняемым представлением является файл DOT (Graphviz) с ограниченным поддерживаемым подмножеством. В памяти граф загружается в типизированную объектную модель. Запись и чтение выполняет `DotCodec`, доступ к файлу — `GraphRepository`.

Поддерживаемое подмножество, правила экранирования, сортировки и диагностики зафиксированы в [docs/dot-storage.md](../dot-storage.md). Неподдерживаемые конструкции отвергаются с диагностикой, а не преобразуются молча.

## Последствия

- Модель можно просматривать, редактировать и сравнивать обычными средствами работы с текстом.
- Файл пригоден для визуализации в Graphviz без дополнительной конвертации.
- Требуется собственный строгий слой разбора: стандартный парсер DOT принимает конструкции, недопустимые для приложения.
- Формат не предназначен для конкурентной записи и больших объёмов; в MVP это ограничение принято.
- Атрибуты оформления Graphviz не сохраняются, чтобы файл оставался моделью данных, а не представлением.

## Рассмотренные альтернативы

- **JSON/YAML.** Проще машинная обработка, но хуже читаемость графа и выше риск потерять структуру при ручном редактировании.
- **SQLite.** Даёт транзакции и конкурентный доступ, но противоречит требованию человекочитаемого файла и усложняет MVP.
- **GraphML/RDF.** Стандартны для графов, но избыточны для первой версии и менее удобны для ручного редактирования.
- **Собственный текстовый формат.** Потребовал бы разработки парсера, редакторов и визуализации без выигрыша для MVP.
