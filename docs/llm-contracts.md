# Контракты взаимодействия с LLM

## 1. Назначение и связанные решения

Документ определяет *независимый от провайдера* протокол запросов к языковой модели, форматы её ответов, проверку данных и предсказуемое поведение при ошибках. 

- [Архитектура компонентов](architecture.md) — распределение ответственности и направление зависимостей.
- [Семантическая модель](semantic-model.md) — `SemanticGraph`, `SemanticNode`, `SemanticEdge`, допустимые типы и атрибуты.
- [Выбор подграфа](subgraph-selection.md) — детерминированный поиск контекста для вопросов и обновлений.
- [Формат патчей](graph-patches.md) — атомарное изменение данных через `GraphPatch`.
- [ADR-0003](adr/0003-llm-proposes-application-applies.md) — LLM предлагает, Python проверяет и применяет.

**Основной принцип:** LLM не получает доступ к файлам, не создаёт устойчивые ID графа и не изменяет DOT. Её ответ — недоверенные данные. Python отдельно проверяет синтаксис JSON, схему, ссылки, подтверждения и доменные инварианты. Только после успешного `PatchValidator`/`PatchApplier` и сохранения графа можно сообщать об изменениях как о выполненных.

## 2. Операции и границы ответственности

| Код операции | Компонент | Вход | Выход | Изменяет граф? |
|---|---|---|---|---|
| `intent.classify` | `IntentClassifier` | Сообщение из автоматического `process` | `IntentDecision` | Нет |
| `knowledge.extract` | `SemanticExtractor` | Текст источника и его ID, назначенный Python | `ExtractionResult`: кандидаты сущностей и отношений | Нет |
| `answer.generate` | `AnswerGenerator` | Вопрос и релевантный подграф | `AnswerResult`: ответ и ID опорных элементов | Нет |
| `changes.explain` | `ChangeExplainer` | Только *фактически применённые и сохранённые* изменения | `ChangeExplanation`: пояснение с привязкой к изменениям | Нет |

Для явных команд CLI (`ask`, `update`, `ingest`) `intent.classify` **не вызывается**: явное намерение имеет приоритет. Извлечение кандидатов не является патчем; сопоставление с графом и получение устойчивых ID выполняют `EntityResolver` и `PatchPlanner`. Формирование структурированного предложения на удаление/обновление в `PatchPlanner` — **отдельный будущий контракт**, не заменяемый `ExtractionResult` и не разрешающий неявного удаления.

Все четыре операции в MVP возвращают **один JSON-объект**. Для `intent.classify` и `knowledge.extract` структурированный JSON обязателен без исключений. Для `answer.generate` и `changes.explain` JSON также обязателен согласно [ADR-0003](adr/0003-llm-proposes-application-applies.md), хотя содержимое поля `answer` или `message` — обычный текст. Ограждения Markdown (например, кодовый блок с пометкой `json`), комментарии, префиксы и дополнительный текст вне объекта запрещены.

## 3. Унифицированный интерфейс LLMGateway

Предлагаемый транспортно-независимый порт (псевдотипы Python):

```python
OperationName = Literal[
    "intent.classify", "knowledge.extract", "answer.generate", "changes.explain"
]

@dataclass(frozen=True)
class LLMMessage:
    role: Literal["system", "user"]
    content: str

@dataclass(frozen=True)
class GenerationParams:
    model: str
    temperature: float
    max_output_tokens: int
    timeout_seconds: float

@dataclass(frozen=True)
class LLMRequest:
    operation: OperationName
    messages: tuple[LLMMessage, ...]
    response_schema: Mapping[str, object]  # JSON Schema 2020-12 для операции
    params: GenerationParams
    prompt_version: str

@dataclass(frozen=True)
class LLMResponse:
    content: str                       # сырой текст, до проверки JSON
    model: str                         # фактически использованная модель
    input_tokens: int | None = None
    output_tokens: int | None = None
    finish_reason: str | None = None

class LLMGateway(Protocol):
    def generate(self, request: LLMRequest) -> LLMResponse: ...
```

`LLMGateway` скрывает SDK, транспорт, авторизацию, преобразование ролей сообщений и особенности JSON-режима конкретной модели. Если провайдер поддерживает `json_schema`/structured output, адаптер передаёт ему схему. Если поддерживает только JSON-mode/текст, адаптер запрашивает JSON, а **проверка в Python остаётся обязательной**. 

**Типовой маршрут:** типизированный вход операции → `PromptRegistry` формирует системное сообщение и отдельное пользовательское сообщение с данными → `LLMGateway.generate` → контроль завершения без обрезания → единственный `json.loads` → проверка JSON Schema/Pydantic (`extra='forbid'`, строгие типы) → семантические проверки → типизированный результат. Промпты не входят в доменный слой; в данном коммите их конкретные `.txt`-файлы не создаются.

Имена операций и версии промптов передаются явно. Поле `contract_version` в каждом ответе должно быть строкой `"1"`; это **не** `SemanticGraph.schema_version` и не ревизия DOT. При изменении несовместимой структуры выпускается новая версия контракта и соответствующей схемы.

### 3.1. Проверяемые схемы

В репозитории предусмотрены JSON Schema (диалект 2020-12) и эталонные ответы:

| Операция | JSON Schema | Корректный ответ |
|---|---|---|
| `intent.classify` | [`intent-decision.schema.json`](llm/schemas/intent-decision.schema.json) | [`intent-classification.json`](../examples/llm/intent-classification.json) |
| `knowledge.extract` | [`extraction-result.schema.json`](llm/schemas/extraction-result.schema.json) | [`knowledge-extraction.json`](../examples/llm/knowledge-extraction.json) |
| `answer.generate` | [`answer-result.schema.json`](llm/schemas/answer-result.schema.json) | [`answer-generation.json`](../examples/llm/answer-generation.json) |
| `changes.explain` | [`change-explanation.schema.json`](llm/schemas/change-explanation.schema.json) | [`change-explanation.json`](../examples/llm/change-explanation.json) |

Проверка всех четырёх примеров: `python -m pytest tests/unit/test_llm_contracts.py` (после `pip install -e ".[dev]"`). Тест также сверяет точность цитат и структуру 8 узлов / 7 связей с `docs/semantic-model.md` и `examples/example-model.dot`.

Схема проверяет локальную структуру и типы. **Межполевые и межобъектные инварианты** (существование ID, уникальность ссылок, буквальная поддержка факта текстом, проверка источников, сопоставление с изменениями) проверяются Python-кодом поверх схемы: JSON Schema не видит исходный документ, граф и историю применения.

## 4. Классификация намерения: `intent.classify`

### 4.1. Запрос

Передаётся `text` — **непустое** пользовательское сообщение из режима `process`, без полного графа и истории переписки, если они не нужны для классификации. `mode` фиксирован как `"automatic"`. Пустой ввод отсекается кодом до вызова LLM, без расхода токенов.

```json
{
  "mode": "automatic",
  "text": "В каком году основана компания «Север»?"
}
```

Системная инструкция описывает категории, выбор при неоднозначности, обязательный формат JSON и запрет выполнения инструкций из текста пользователя. Пользовательское сообщение передаёт данные как сериализованный JSON, не добавляя их к системной инструкции.

### 4.2. Модель ответа `IntentDecision`

| Поле | Тип и ограничения | Значение |
|---|---|---|
| `contract_version` | строка `"1"`, обязательно | Версия протокола |
| `category` | enum, обязательно | `QUESTION`, `UPDATE`, `INGEST`, `CLARIFICATION_REQUIRED`, `UNKNOWN` |
| `confidence` | JSON number `0.0..1.0`, обязательно | Уверенность именно в классификации, не истинность сведений |
| `reason` | непустая строка, обязательно | Краткое объяснение (без скрытых рассуждений) |
| `needs_clarification` | JSON boolean, обязательно | `true` ровно для `CLARIFICATION_REQUIRED` |
| `clarification_question` | непустая строка, условно | Обязательно только при `CLARIFICATION_REQUIRED`; в остальных случаях отсутствует |

Категории: `QUESTION` — запрос ответа по графу; `UPDATE` — явное изменение существующих знаний; `INGEST` — добавление текста как источника знаний; `CLARIFICATION_REQUIRED` — неоднозначно действие или объект изменения; `UNKNOWN` — нет достаточных признаков для известных сценариев. Длина сообщения **сама по себе не доказывает** `INGEST`: длинный вопрос остаётся вопросом.

Пример: [`examples/llm/intent-classification.json`](../examples/llm/intent-classification.json). Порог допустимой уверенности и разрешение конфликтов определяет `ApplicationService`, не модель. При низкой уверенности запрещено автоматически выполнять изменения. Некорректная категория или `confidence` не заменяются догадкой/значением по умолчанию.

## 5. Извлечение знаний: `knowledge.extract`

### 5.1. Запрос

```json
{
  "source_ref": "doc_example_001",
  "text": "Компания «Север» основана Анной Смирновой в 2018 году. В 2021 году компания выпустила программный продукт «Орбита». Продукт предназначен для анализа документов."
}
```

`source_ref` назначает приложение при приёме текста, **не LLM**. В промпте передаётся только текущий фрагмент источника и закрытые списки `NodeType`/`ValueKind`; *полный* существующий граф не нужен. При точечном обновлении релевантный контекст передаётся отдельному обработчику, если требуется, но результат извлечения сам по себе не определяет операции над существующими ID.

### 5.2. Модель ответа `ExtractionResult`

```text
ExtractionResult
  contract_version: Literal["1"]
  entities: list[ExtractedEntity]
  relations: list[ExtractedRelation]
  warnings: list[str]

ExtractedEntity
  local_id: str                  # только локальная ссылка внутри этого ответа
  name: str                      # отображаемое имя кандидата
  type: NodeType                 # object/person/organization/event/concept/value
  mention: str                   # ДОСЛОВНАЯ подстрока входного текста
  description?: str
  value_kind?: ValueKind         # обязателен только при type=value
  value?: str                    # обязателен только при type=value

ExtractedRelation
  local_id: str                  # локальная ссылка утверждения
  source_local_id: str          # ссылается на entity.local_id
  target_local_id: str          # ссылается на entity.local_id
  relation: str                  # [a-z][a-z0-9_]*, направление субъект -> объект
  evidence: str                  # ДОСЛОВНАЯ непустая подстрока текста
  confidence?: float            # 0.0..1.0, без значения по умолчанию
```

**Правила:**

1. `entities`, `relations`, `warnings` всегда присутствуют, даже если пусты. Если фактов нет, допустим `{ "entities": [], "relations": [], "warnings": [] }` вместе с `contract_version`. Это *корректный результат без знаний*.
2. `local_id` уникален внутри собственного массива и нужен только для соединения кандидатов; не является устойчивым `SemanticNode.id`/`SemanticEdge.id` и не сохраняется в DOT. Запрещено использовать его как ссылку на существующий граф.
3. `source_local_id` и `target_local_id` должны ссылаться на объявленные `entities.local_id`. Самоссылки и параллельные отношения допускаются, но ссылки на отсутствующие кандидаты — ошибка.
4. `mention` каждого кандидата и `evidence` каждого утверждения обязаны **в точности встречаться** во входном `text` как подстроки; перефразированная «цитата» отклоняется. Выводить факты на основе общеизвестности запрещено. Сведения, которые текст не позволяет установить, не извлекаются; неопределённость кратко фиксируется в `warnings`.
5. `type` и `value_kind` совпадают со [спецификацией модели](semantic-model.md). Если `type = "value"`, присутствуют оба поля `value_kind` и `value`; для иных типов оба отсутствуют. Нельзя автоматически менять неизвестный тип на `concept`.
6. `relation` использует `snake_case`; направление выражено явными ссылками. Отрицание, гипотеза и предположение не превращаются в безусловное положительное утверждение. Источник (`source_ref`) Python присваивает кандидатным связям после проверки, а не принимает обратно из ответа LLM.
7. `confidence` относится к качеству извлечения **отдельного** утверждения, не означает вероятность объективной истинности; отсутствие поля не означает `1.0`. `NaN`, `Infinity` и строковые числа недопустимы.
8. Очевидные дубликаты в одном ответе можно устранить детерминированно после валидации при условии сохранения происхождения и ссылочной целостности. Совпадающие имена **не** служат доказательством тождества разных сущностей; `EntityResolver` отдельно разбирает неоднозначность.
9. Если хотя бы одна обязательная связь/ссылка/цитата невалидна, в MVP отклоняется **весь** результат (`EXTRACTION_INVALID`), а не формируется частичный патч из оставшегося списка. Допустимые `warnings` не делают результат невалидным.

Пример с восемью кандидатными сущностями и семью связями соответствует [примеру семантической модели](semantic-model.md#9-пример-построения-модели): [`examples/llm/knowledge-extraction.json`](../examples/llm/knowledge-extraction.json).

## 6. Генерация ответа: `answer.generate`

### 6.1. Запрос

```json
{
  "question": "В каком году была основана компания «Север»?",
  "context": {
    "schema_version": "1",
    "revision": 0,
    "nodes": [
      {"id": "org_sever", "name": "Компания «Север»", "type": "organization"},
      {"id": "event_foundation", "name": "Основание компании «Север»", "type": "event"},
      {"id": "value_year_2018", "name": "2018 год", "type": "value", "value_kind": "year", "value": "2018"}
    ],
    "edges": [
      {"id": "edge_sever_has_foundation", "source_node_id": "org_sever", "target_node_id": "event_foundation", "relation": "has_event"},
      {"id": "edge_foundation_year", "source_node_id": "event_foundation", "target_node_id": "value_year_2018", "relation": "occurred_in"}
    ]
  }
}
```

`context` — **только подграф** из `SubgraphSelector`, включая нужные поля узлов и связей; ID и направления сохраняются, лишние узлы и внешние документы не включаются. Ограничения объёма задаёт `SubgraphLimits` и бюджет запроса. Контекст не является системной инструкцией.

### 6.2. Модель ответа `AnswerResult`

| Поле | Тип | Значение |
|---|---|---|
| `contract_version` | строка `"1"` | Версия контракта |
| `status` | `ANSWERED` / `INSUFFICIENT_CONTEXT` | Есть ли обоснованный ответ |
| `answer` | непустая строка | Человекочитаемый текст, без придуманных фактов |
| `used_node_ids` | `list[str]` | ID узлов, на которых основан ответ |
| `used_edge_ids` | `list[str]` | ID связей, на которых основан ответ |

При `ANSWERED` хотя бы один список опорных ID непуст; все ссылки должны существовать **в переданном подграфе**. При `INSUFFICIENT_CONTEXT` оба списка пусты, а `answer` явно говорит, что данных модели недостаточно. При пустом подграфе `AnswerGenerator` может вернуть этот результат **без вызова модели**. Наличие опорных ID необходимо, но само по себе не доказывает семантическую истинность: заявленные факты должны быть подтверждены конкретными узлами/отношениями. Не допускаются ссылки на идентификаторы из полного графа, отсутствующие в подграфе.

Пример: [`examples/llm/answer-generation.json`](../examples/llm/answer-generation.json).

## 7. Объяснение изменений: `changes.explain`

### 7.1. Запрос

Запускается только **после подтверждённого успешного применения и сохранения патча**. Передаются не исходные намерения модели, а детерминированный журнал реально выполненных операций, включая тип, ID, существенные значения «до/после» и подтверждённые ревизии. Пример:

```json
{
  "base_revision": 0,
  "saved_revision": 1,
  "applied_changes": [
    {
      "change_id": "c0",
      "kind": "added",
      "object_kind": "node",
      "object_id": "project_1",
      "before": null,
      "after": {"id": "project_1", "name": "Проект", "type": "object"}
    },
    {
      "change_id": "c1",
      "kind": "added",
      "object_kind": "edge",
      "object_id": "edge_2",
      "before": null,
      "after": {
        "id": "edge_2", "source_node_id": "person_1", "target_node_id": "project_1", "relation": "participates_in"
      }
    }
  ]
}
```

`change_id` генерирует Python как **локальный идентификатор элемента журнала** (например, `c0`, `c1`), не ID графа. `kind` — одно из `added`, `updated`, `deleted`. Для удаления `after = null`, для обновления присутствуют оба состояния. Промпт требует описывать только перечисленные изменения, с разделением добавленных, изменённых и удалённых фактов, без утверждений о неуспешных патчах.

### 7.2. Модель ответа `ChangeExplanation`

| Поле | Тип | Значение |
|---|---|---|
| `contract_version` | строка `"1"` | Версия контракта |
| `status` | `EXPLAINED` / `NO_CHANGES` | Результат объяснения |
| `message` | непустая строка | Компактное понятное пояснение |
| `items` | массив объектов | По одному пояснению на реально выполненное изменение |
| `items[].change_id` | строка | ID операции из `applied_changes` |
| `items[].kind` | `added` / `updated` / `deleted` | Точный тип действия из журнала |
| `items[].text` | непустая строка | Описание только этого действия |

Для `EXPLAINED` `items` содержит **ровно все** `change_id` из запроса, без пропусков и дубликатов, с неизменёнными `kind`; если их нет — ответ недопустим. Для `NO_CHANGES` список пуст, и такой результат выдаётся локально **без вызова LLM**. Проверка ссылок и полноты выполняется после JSON Schema. Пользовательское сообщение о сохранении допускается только после успеха репозитория.

Если LLM недоступна, ответ пуст, невалиден, необоснован или превышает лимит, `ChangeExplainer` формирует **детерминированное описание из журнала Python**, без выдуманных фактов и без повторного изменения графа.

Пример: [`examples/llm/change-explanation.json`](../examples/llm/change-explanation.json).

## 8. Обработка ошибок, пустоты и частичных ответов

Порядок проверки одинаков для всех операций: 1) ошибка транспорта или тайм-аут; 2) пустой или обрезанный ответ; 3) строгий разбор единственного JSON-объекта с отклонением повторяющихся ключей и нечисловых констант `NaN`/`Infinity` (`object_pairs_hook` и `parse_constant` в стандартном `json.loads`); 4) схема и поля; 5) семантические ограничения; 6) преобразование к типизированной модели. **Не** извлекать JSON регулярными выражениями из «окружающего текста», не дополнять отсутствующие поля и не исправлять некорректное содержимое с помощью догадок.

| Ситуация | Решение в MVP |
|---|---|
| `content == ""`, пробельный ответ или отсутствующее тело | `LLM_INVALID_RESPONSE`; не считать пустым массивом знаний |
| Только `{}` / отсутствуют обязательные поля | Ошибка проверки схемы; нельзя подставлять `UNKNOWN`, `[]`, `0` и т. п. |
| Обрезанный по лимиту ответ, `finish_reason` указывает на truncation | `LLM_INVALID_RESPONSE`, даже если начало выглядит допустимым |
| Не JSON, массив вместо объекта, несколько объектов, Markdown-обёртка | `LLM_INVALID_RESPONSE`, отказ без «починки» |
| Неизвестные ключи, неверный тип, enum, диапазон, не-числовое `confidence`, `null` вместо обязательного поля | Ошибка схемы; `extra='forbid'`, строгая валидация |
| Корректный JSON, но неверная ссылка на entity/node/change, вымышленная цитата или нарушение условного ограничения | Ошибка семантической проверки, результат целиком отклонён |
| Валидное извлечение `entities=[]`, `relations=[]`, `warnings=[]` | Нормальное отсутствие найденных фактов; не создавать патч |
| Валидное `INSUFFICIENT_CONTEXT` или пустой подграф | Нормальное сообщение о нехватке знаний; DOT не меняется |
| Пустой журнал применённых изменений | Локальное объяснение `NO_CHANGES`; LLM не вызывается |
| Провайдер недоступен / ограничил запрос / тайм-аут | `LLM_UNAVAILABLE` / `LLM_RATE_LIMIT` / `LLM_TIMEOUT` (соответственно) |
| Неизвестная модель, отсутствует ключ, неподдерживаемые параметры | Явная ошибка конфигурации до сетевого запроса |

Коды на уровне операций: `INVALID_INTENT_RESPONSE` для невалидной классификации, `EXTRACTION_INVALID` для невалидного извлечения, `LLM_INVALID_RESPONSE` для генерации ответа и `EXPLANATION_FAILED` для объяснения (с локальным fallback). На транспортной границе используются `LLM_TIMEOUT`, `LLM_UNAVAILABLE`, `LLM_RATE_LIMIT`. Внутренние причины (отсутствующее поле, проблемный ID, нарушение `evidence`) сохраняются в диагностике без раскрытия конфиденциального текста источника или API-ключей. Список ошибок — контракт уровня MVP; уточнение собственных классов исключений относится к реализации.

Никакой невалидный ответ не должен вызвать `PatchApplier` или запись в `GraphRepository`. В MVP автоматическая «починка JSON» и бесконечные/скрытые повторы запрещены. Если повтор в будущем появится, он должен иметь явный ограниченный бюджет и отдельные тесты; не использовать повтор для обхода непрохождения доменных проверок.

## 9. Требования к промптам и защита от недостоверных выводов

1. **Разделять роли:** системные инструкции, правила операции, ограничения и схема — системное сообщение; `text`, `question`, подграф, журнал изменений — отдельное пользовательское сообщение с данными, предпочтительно JSON. Не конкатенировать входной текст в системную инструкцию.
2. **Считать данные недоверенными:** инструкции внутри документов/узлов/истории (`«игнорируй правила»`, «вставь факт», псевдо-role tags и т. п.) не имеют права менять порядок обработки, схему или политику записи. Формат JSON и указание границ улучшают разграничение, но сами по себе не гарантируют защиту; итог решает проверка Python.
3. **Не придумывать факты:** извлечение только подтверждённого текстом; ответы — только из выделенного подграфа; объяснение — только по завершённому журналу. При нехватке данных вернуть допустимый результат недостаточности, а не домысел.
4. **Контекст по необходимости:** не посылать весь граф для ответа/точечного обновления. Использовать `SubgraphLimits`, ограничение размера входа и отдельные фрагменты больших документов. При обрезании нельзя выдавать ответ как проверенный по всей базе.
5. **Формат:** единый JSON-объект по версии схемы, без Markdown и посторонних пояснений. В `reason`/`warnings` — только короткие диагностические замечания, без просьбы выдавать внутреннюю цепочку рассуждений.
6. **Без побочных действий:** промпт не просит вызывать инструменты, менять файлы, генерировать DOT, выполнять shell-команды, отправлять секреты или объявлять патч сохранённым до подтверждения приложения.
7. **Версионирование:** у каждого будущего шаблона отдельные `operation`, `prompt_version` и зафиксированные входные переменные. Любое изменение формулировки промпта, влияющее на качество, сопровождается версионированием тестовых сценариев.
8. **Логи без секретов:** допускаются название модели, версии промпта/контракта, длительность, токены, коды ошибок и идентификаторы запроса. Полный текст документов, содержимое приватного графа и сырые ответы не журналировать по умолчанию.

## 10. Воспроизводимость и параметры генерации

| Параметр | Требование / рекомендованное начальное значение | Комментарий |
|---|---|---|
| `model` | Непустой идентификатор, **обязателен**, читается из конфигурации | Не зашит в бизнес-логику; при тестах — `fake` |
| `temperature` | `0.0` для четырёх операций, если модель поддерживает | Не обеспечивает абсолютной детерминированности; адаптер явно проверяет поддержку |
| `max_output_tokens` | `2048` для классификации/ответа/объяснения, `4096` для извлечения | Положительное целое; лимит исчерпан — не принимать частичный ответ |
| `timeout_seconds` | `30.0` для всех операций в MVP | Положительное конечное число; настройка на стороне клиента |
| `prompt_version` | Например, `1` для начальных шаблонов | Логировать отдельно от версии схемы |
| `contract_version` | Строго `"1"` | Проверять в каждом ответе |
| `seed` | Необязателен и только при поддержке провайдера | Не считать переносимой гарантией воспроизводимости |

Для повторяемых экспериментов фиксируют модель и её доступную версию, параметры, версию промпта и схему, точный вход и фикстуру ответа. Модель, `temperature=0` и тот же промпт **не гарантируют** побайтово одинаковых результатов на всех провайдерах; для стабильных тестов используется `FakeLLMGateway`.

## 11. Требования к FakeLLMGateway

Фиктивный провайдер реализует **тот же порт** `LLMGateway.generate`, что и реальный адаптер, без интернета, SDK, ключей или переменных окружения с секретами.

- На вход получает `LLMRequest` целиком. Настраивается очередью подготовленных ответов/исключений **с ожидаемым `operation`**; не содержит собственной классификации и не генерирует факты.
- Возвращает ровно заданный `LLMResponse` с `model="fake"`, включая намеренно пустые, неполные, неверные JSON-ответы для негативных тестов. При необходимости эмулирует `LLM_TIMEOUT`, `LLM_UNAVAILABLE` и `LLM_RATE_LIMIT` без сна и сети.
- Запоминает историю вызовов (`operation`, сообщения, параметры, версию промпта, схему) для проверки порядка, количества вызовов, границ переданного контекста и запрета лишнего обращения.
- При неожиданном типе операции, лишнем вызове или неиспользованном ответе выдаёт тестовую диагностическую ошибку; тесты должны уметь проверить полное потребление сценария.
- Работает одинаково при повторном запуске; не использует случайность и время. С помощью очереди позволяет задать цепочки `classify → extract`, `classify → answer` и отрицательные ветви.
- Тесты проверяют: успешную валидацию каждого примера; `UNKNOWN`/`CLARIFICATION_REQUIRED`; отсутствие фактов/подграфа; пустоту/обрезание/неправильный JSON; неверные ссылки и цитаты; изоляцию от DOT; fallback объяснения; заданный порядок вызовов и отсутствие сетевого доступа.

Базовые JSON-ответы и их схемы из §3.1 — эталонные фикстуры для реализации и тестирования. Не использовать фикстуры в качестве команд на создание/изменение графа.

## 12. Критерии приёмки 

- Есть четыре операции с отдельными, провайдерно-независимыми входными и выходными контрактами.
- Классификация и извлечение обязательно используют JSON; ответы и объяснения также имеют строго типизированный JSON согласно ADR.
- `IntentDecision`, `ExtractionResult` и их ограничения однозначны; пример извлечения согласован со схемой семантического графа.
- Определены проверки пустого/частичного/некорректного ответа и запрещено молчаливое исправление или частичное изменение графа.
- Описаны требования к промптам, настройкам генерации и `FakeLLMGateway` без внешнего API.
- Предоставлены четыре корректных JSON-ответа и четыре машинно-проверяемые схемы; последующие разработчики могут независимо реализовать адаптер, классификатор и извлекатель.
