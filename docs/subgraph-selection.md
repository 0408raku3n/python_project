# Выбор релевантного подграфа

## Статус и границы

Документ описывает детерминированный алгоритм поиска части семантической модели для ответа на вопрос или запроса на обновление. Алгоритм не использует LLM и проверяется на заранее известных графах.

Формат хранения и идентификаторы определены в [dot-storage.md](dot-storage.md), изменения графа — в [graph-patches.md](graph-patches.md), место компонента в системе — в [architecture.md](architecture.md). Спецификация семантической модели ещё не написана, поэтому типы сущностей и дополнительные текстовые атрибуты предварительны: сейчас в DOT гарантированно существует только `label`. До появления `docs/semantic-model.md` фильтр по типам считается неприменимым, а поиск идёт по названиям.

## Термины

- **Исходный граф** — загруженная и проверенная `SemanticGraph`, которая не изменяется при поиске.
- **Подграф** — набор узлов и связей исходного графа, выбранный для обработки запроса.
- **Начальный узел (seed)** — узел, непосредственно совпавший с запросом по названию, типу или ключевому слову.
- **Релевантный подграф** — начальные узлы вместе с ограниченной окрестностью. Он не обязан быть деревом: в модели допустимы циклы, петли и несколько связей между одной парой узлов. Встречающийся в плане термин «поддерево ответа» означает именно этот подграф, а не математическое дерево.
- **Бюджет** — максимальное число узлов и связей в результате.

## Вход и выход

Компонент `SubgraphSelector` имеет один интерфейс для вопросов и запросов на обновление; сценарий не меняет алгоритм поиска.

```python
@dataclass(frozen=True)
class SubgraphLimits:
    max_nodes: int = 64
    max_edges: int = 128
    depth: int = 2
    max_seeds: int = 5
    min_score: int = 20


@dataclass(frozen=True)
class NodeMatch:
    node_id: str
    score: int
    reasons: tuple[str, ...]


@dataclass(frozen=True)
class SubgraphQuery:
    text: str
    intent: IntentCategory          # QUESTION или UPDATE; влияет только на политику вызывающего кода
    entity_types: frozenset[str] = frozenset()
    keywords: tuple[str, ...] = ()
    limits: SubgraphLimits = SubgraphLimits()


@dataclass(frozen=True)
class SubgraphSelection:
    graph: SemanticGraph            # выбранные узлы и связи; ревизия исходного графа
    matches: tuple[NodeMatch, ...]  # узел, баллы, основание совпадения
    outcome: SelectionOutcome       # MATCHED, NO_MATCH, EMPTY_GRAPH
    ambiguous: bool
    candidates: tuple[NodeMatch, ...]  # конкурирующие начальные узлы при неоднозначности
    truncated: bool                 # бюджет не позволил включить часть окрестности
    terms: tuple[str, ...]          # нормализованные термины запроса
```

`SubgraphSelector.select(graph, query) -> SubgraphSelection` — чистая функция: не обращается к LLM, файлам и CLI, не изменяет исходный граф. Возвращённый `graph` — производное представление для чтения, а не новое сохраняемое состояние; его `revision` и `schema_version` совпадают с исходными.

Для вопросов достаточно передать текст, для обновлений — текст запроса и, при наличии, предполагаемые типы или ключевые слова. Явные команды CLI не требуют классификации намерения; поле `intent` используется прикладным слоем для политики уточнения.

## Ограничения и значения по умолчанию

| Параметр | По умолчанию | Допустимый диапазон | Смысл |
|---|---:|---:|---|
| `max_nodes` | 64 | 1–500 | Максимум узлов в результате, включая начальные. |
| `max_edges` | 128 | 0–2000 | Максимум связей в результате. |
| `depth` | 2 | 0–5 | Максимальное расстояние от начального узла. |
| `max_seeds` | 5 | 1–50 | Максимум начальных узлов. |
| `min_score` | 20 | 0–200 | Минимальный балл, чтобы узел считался начальным. |

Дополнительно требуется `max_seeds <= max_nodes`; иначе возвращается `INVALID_LIMIT`. `depth = 0` означает «только начальные узлы, без связей». Параметры задаются конфигурацией и могут переопределяться аргументами CLI; значения по умолчанию не должны приводить к выгрузке всего графа на типовых моделях.

## Нормализация запроса

1. Применить Unicode NFKC, привести к нижнему регистру и свернуть повторяющиеся пробелы.
2. Выделить токены как последовательности букв, цифр и `_`. Кавычки в запросе задают фразу, которая ищется как единое целое.
3. Удалить пустые токены, токены длиной менее двух символов и стоп-слова (небольшой список русских и английских служебных слов). Порядок терминов сохраняется, повторы удаляются.
4. Ограничить число терминов (по умолчанию 32), чтобы запрос не разрастался.
5. Не применять тяжёлую морфологию и стемминг в MVP: используется точное совпадение и сравнение префиксов. Стемминг и лемматизация остаются возможным расширением.

Нормализация применяется только к поиску. Исходный текст запроса передаётся в LLM без изменений и рассматривается как данные, а не как инструкция.

## Оценка узлов

Баллы начисляются за совпадение с названием (`label`) и, если спецификация модели добавит текстовые атрибуты, с поддерживаемыми ключевыми словами. Значения сравниваются после той же нормализации. В MVP начальные узлы выбираются только по узлам: названия связей не порождают начальный узел, иначе запрос «работает» необоснованно расширял бы контекст.

| Признак | Баллы |
|---|---:|
| Нормализованное `label` целиком равно термину или фразе | 100 |
| `label` содержит фразу или термин как подстроку | 60 |
| Токен `label` точно равен термину | 40 |
| Токен `label` начинается с термина либо термин начинается с токена, при длине не менее 4 символов | 20 |
| Совпадение с ключевым словом из `keywords` | 20 за термин, не более 40 |
| Совпадение с дополнительным текстовым атрибутом (после расширения модели) | 10 |

Баллы за разные термины суммируются, итог ограничивается 120. Для одного термина берётся лучший признак, а не сумма всех. Совпадение названий чувствительно к Unicode-нормализации, но не к регистру.

Если задан `entity_types`, узел участвует в поиске только при совпадении типа. Узел без известного типа при непустом фильтре исключается. До появления типов в DOT фильтр должен быть пустым; иначе результат предсказуемо пуст, а не подменяется догадками.

## Выбор начальных узлов и неоднозначность

1. Отобрать узлы с баллом `>= min_score`.
2. Отсортировать по убыванию балла, затем по идентификатору узла — для воспроизводимости.
3. Оставить не более `max_seeds`.
4. Если после отбора осталось два и более узла с одинаковым лучшим баллом либо второй балл не меньше 90% лучшего, установить `ambiguous = true` и заполнить `candidates` всеми узлами в пределах допуска.

Политика вызывающего кода:

- **QUESTION.** Неоднозначность допустима: все отобранные начальные узлы попадают в контекст, если позволяют лимиты. Ответ строится по объединённой окрестности; при нехватке данных система сообщает о недостаточности контекста.
- **UPDATE.** Если неоднозначность затрагивает цель изменения, прикладной слой возвращает `CLARIFICATION_REQUIRED` и не формирует патч. Автоматический выбор одного из равнозначных узлов запрещён, чтобы не изменить не ту сущность.
- **Более `max_seeds` кандидатов.** Выбираются лучшие по баллам; остальные попадают в `candidates`. `truncated` в этом случае не устанавливается: ограничение числа начальных узлов — заданная политика, а не нехватка бюджета.

## Обход окрестности

Обход выполняется в ширину от начальных узлов. Начальные узлы имеют расстояние 0 и включаются первыми; при нехватке `max_nodes` они имеют приоритет над соседями.

Для узла на расстоянии `d` рассматриваются все инцидентные связи (входящие и исходящие), отсортированные по ключу `(сосед_уже_выбран, идентификатор_соседа, идентификатор_связи)`. Сначала обрабатываются связи, ведущие к ещё не выбранным узлам, — так расширение не блокируется внутренними связями.

- Если соседний узел уже выбран, связь добавляется при наличии бюджета связей. Это сохраняет циклы, петли и параллельные связи.
- Если соседний узел не выбран и `d < depth` и есть место в бюджете узлов, добавляются узел и связь, узел помещается в очередь с расстоянием `d + 1`.
- Если сосед не может быть добавлен из-за `depth`, связи нет: висячих связей в результате не бывает.
- Если сосед не добавлен из-за бюджета узлов или связей, изменение отмечается как `truncated = true`.
- Повторно обработанные узлы и уже выбранные связи пропускаются; циклы не приводят к зацикливанию.

Связь включается только вместе с обоими концами. Узел, не являющийся начальным, включается только вместе хотя бы с одной связью. После завершения обхода результат проверяется теми же инвариантами, что и обычный граф: уникальность ID и наличие обоих концов каждой связи.

Порядок обхода и сортировки полностью детерминирован. Одинаковые исходный граф, запрос и лимиты дают одинаковый набор ID узлов и связей.

## Пустой результат

| Ситуация | `outcome` | Поведение |
|---|---|---|
| В исходном графе нет узлов | `EMPTY_GRAPH` | Подграф пуст; вызывающий код сообщает, что модель ещё не построена. |
| Ни один узел не набрал `min_score` | `NO_MATCH` | Подграф пуст; ответ на вопрос — insufficient context, обновление не выполняется. |
| Все кандидаты отфильтрованы по типу | `NO_MATCH` | То же; тип не подменяется угадыванием. |
| Запрос пуст или состоит только из стоп-слов | `NO_MATCH` | Уточнение запроса; весь граф не возвращается. |

При пустом результате запрещено автоматически возвращать весь граф или отдельный узел «по умолчанию». Запасной вариант — явное сообщение пользователю и предложение уточнить запрос.

## Детерминизм и сложность

Алгоритм не использует случайность, время и порядок обхода словаря. Все сортировки имеют полный ключ, включая ID. Сложность — `O((V + E) log V)` в худшем случае без учёта бюджета; на практике обход ограничен `depth`, `max_nodes` и `max_edges`, поэтому стоимость зависит от размера результата, а не только от графа.

## Псевдокод

```python
def select(graph: SemanticGraph, query: SubgraphQuery) -> SubgraphSelection:
    validate_limits(query.limits)                 # иначе INVALID_LIMIT
    if not graph.nodes:
        return empty_selection(EMPTY_GRAPH, query)

    terms = normalize_terms(query.text, query.keywords)
    scored = []
    for node in graph.nodes:
        if query.entity_types and node.type not in query.entity_types:
            continue
        score, reasons = score_node(node, terms)
        if score >= query.limits.min_score:
            scored.append(NodeMatch(node.id, score, reasons))

    scored.sort(key=lambda m: (-m.score, m.node_id))
    seeds = scored[: query.limits.max_seeds]
    ambiguous, candidates = detect_ambiguity(scored, seeds)
    if not seeds:
        return empty_selection(NO_MATCH, query, terms=terms)

    selected_nodes = {m.node_id: graph.node(m.node_id) for m in seeds}
    selected_edges = {}
    queue = deque((m.node_id, 0) for m in seeds)
    truncated = False

    while queue:
        node_id, distance = queue.popleft()
        incidents = sorted(
            graph.incident_edges(node_id),
            key=lambda e: (
                other(e, node_id) in selected_nodes,
                other(e, node_id),
                e.id,
            ),
        )
        for edge in incidents:
            if edge.id in selected_edges:
                continue
            neighbour = other(edge, node_id)
            if neighbour in selected_nodes:
                if len(selected_edges) < query.limits.max_edges:
                    selected_edges[edge.id] = edge
                else:
                    truncated = True
                continue
            if distance >= query.limits.depth:
                continue                        # глубина — не усечение
            if len(selected_nodes) >= query.limits.max_nodes:
                truncated = True
                continue
            if len(selected_edges) >= query.limits.max_edges:
                truncated = True
                continue
            selected_nodes[neighbour] = graph.node(neighbour)
            selected_edges[edge.id] = edge
            queue.append((neighbour, distance + 1))

    result_graph = build_subgraph(graph, selected_nodes, selected_edges)
    assert valid_subgraph(result_graph)              # оба конца, уникальные ID
    return SubgraphSelection(
        graph=result_graph,
        matches=tuple(seeds),
        outcome=MATCHED,
        ambiguous=ambiguous,
        candidates=tuple(candidates),
        truncated=truncated,
        terms=terms,
    )
```

`build_subgraph` сохраняет `schema_version` и `revision` исходного графа, но не является сохраняемым состоянием. `graph.incident_edges` и `graph.node` — операции доступа доменной модели; они не мутируют граф.

## Примеры

### Вопрос по известному графу

Исходный граф — [valid.dot](../examples/dot/valid.dot): `person_1` («Анна "Аня" Иванова»), `team_1` («Отдел аналитики / Исследования»), связь `edge_1` («работает в»).

Запрос: `Где работает Анна?`, лимиты по умолчанию.

- Термины после удаления стоп-слов: `работает`, `анна`; «работает» не совпадает с названиями узлов, «анна» — токен `person_1`.
- Начальный узел: `person_1` (балл 40 за точный токен).
- Обход глубины 1 добавляет `team_1` и `edge_1`.

Результат: узлы `person_1`, `team_1`; связь `edge_1`; `outcome = MATCHED`, `ambiguous = false`, `truncated = false`.

### Пустой результат

Запрос: `Какая погода в Москве?` к тому же графу.

Ни один термин не даёт балл `>= 20`: `outcome = NO_MATCH`, подграф пуст, `matches` пуст. Ответ должен сообщить о недостаточности контекста, а не выдумывать факт.

### Неоднозначность

Граф содержит `person_1` («Анна Иванова») и `person_2` («Анна Петрова»). Запрос: `Анна`.

Оба узла получают 100 баллов, `ambiguous = true`, `candidates` содержит оба. Для `QUESTION` оба попадают в контекст; для `UPDATE` прикладной слой запрашивает уточнение.

### Ограничение бюджета

Тот же `valid.dot`, запрос `Анна`, `max_nodes = 1`, `max_edges = 0`, `max_seeds = 1`, `depth = 1`.

Результат: только `person_1`, связей нет, `truncated = true`: связь нельзя включить без второго узла. Ограничение по глубине само по себе (`depth = 0`) не делает результат усечённым, если окрестность не запрашивалась.

### Цикл и параллельные связи

Граф `a -> b`, `b -> c`, `c -> a`, плюс две связи `a -> b` с разными ID. Запрос `a`, `depth = 3`.

Результат содержит все три узла и все связи; повторный обход не зацикливается, параллельные связи сохраняются, если хватает бюджета. Это подтверждает, что результат — подграф, а не дерево.

## Тестирование

Функциональные и модульные тесты не требуют LLM, сети и файловой системы. Минимальный набор фикстур:

1. пустой граф — `EMPTY_GRAPH`;
2. граф без совпадений — `NO_MATCH`;
3. линейная цепочка — корректная глубина и границы;
4. граф с циклом и петлёй — завершение обхода и сохранение связей;
5. параллельные связи — сохранение всех связей в пределах бюджета;
6. два узла с одинаковым названием — `ambiguous` и политика уточнения;
7. ограничение `max_nodes` — приоритет начальных узлов и `truncated`;
8. ограничение `max_edges` — отсутствие висячих связей и `truncated`;
9. `depth = 0` — только начальные узлы;
10. Unicode и регистр — «анна», «АННА», «Анна» дают одинаковый результат;
11. детерминизм — повторный вызов возвращает тот же набор ID при другом порядке объявлений в DOT;
12. неверные лимиты — `INVALID_LIMIT`.

Критерий приёмки: для каждого примера из раздела выше результат воспроизводим и проверяется по ID, а не по текстовому представлению DOT.

## Расширение семантическим ранжированием

Интерфейс допускает замену функции оценки без изменения обхода:

```python
class NodeRanker(Protocol):
    def score(
        self,
        node: SemanticNode,
        terms: tuple[str, ...],
        graph: SemanticGraph,
    ) -> float: ...
```

Планируемое развитие:

- комбинировать лексический балл с семантическим сходством (эмбеддинги названий и описаний);
- кэшировать векторы узлов и инвалидировать кэш при изменении узла;
- калибровать порог и веса на контрольном наборе запросов;
- при недоступности модели сходства откатываться к текущему детерминированному алгоритму;
- ранжировать только начальные узлы; обход окрестности остаётся структурным.

Семантическое ранжирование не входит в MVP и не должно делать основные тесты зависимыми от сети или API-ключей.
